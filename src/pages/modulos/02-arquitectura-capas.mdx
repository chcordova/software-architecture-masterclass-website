export const codeHexagonalDomain = `
package com.company.attendance.domain.model;

import com.company.attendance.domain.exception.FutureDateException;
import com.company.attendance.domain.exception.InvalidAttendanceException;
import java.time.LocalDateTime;

public class Attendance {

    private final Long id;
    private final Long employeeId;
    private final LocalDateTime timestamp;
    private final AttendanceType type;

    public Attendance(Long id, Long employeeId, LocalDateTime timestamp, AttendanceType type) {
        this.id = id;
        this.employeeId = employeeId;
        this.timestamp = timestamp;
        this.type = type;
        validate();
    }

    public void validate() {
        if (employeeId == null || employeeId <= 0) {
            throw new InvalidAttendanceException("Employee ID must be positive.");
        }
        if (timestamp == null) {
            throw new InvalidAttendanceException("Timestamp is mandatory.");
        }
        if (timestamp.isAfter(LocalDateTime.now())) {
            throw new FutureDateException(timestamp);
        }
        if (type == null) {
            throw new InvalidAttendanceException("Attendance type is mandatory.");
        }
    }

}
`;

# Módulo 2: Arquitectura en Capas (Teoría vs. Código)

En este módulo contrastaremos la teoría clásica del patrón de **Arquitectura en Capas (Layered / 3-Tier Architecture)** con la implementación real del repositorio `attendance-service-layered`.

## 2.1 Teoría: Particionamiento Técnico y Aislamiento

La **Arquitectura en Capas** organiza el código fuente aplicando un **particionamiento técnico** (_Technical partitioning_). Los componentes se agrupan horizontalmente según su rol tecnológico: Presentación, Lógica de Negocio (Servicio), Persistencia y Base de Datos.

### Separación de Responsabilidades y MVC

Este modelo sigue el principio de **Separation of Concerns (SoC)** y guarda una fuerte relación con el patrón **MVC (Model-View-Controller)**:

- **Capas de Aislamiento (Layers of Isolation):** En un modelo cerrado, una capa solo se comunica de forma descendente con la capa inmediatamente inferior. Esto permite sustituir la persistencia sin alterar la presentación.

<Callout title="Ventajas Clave" type="tip">
  * **Estructura intuitiva:** Alta familiaridad para equipos organizados por
  especialidad técnica (Frontend, Backend, DBAs). * **Baja complejidad
  inicial:** Ideal para aplicaciones sencillas, prototipos y CRUDs básicos.
</Callout>

### Desventajas y Antipatrones

1. **Architecture Sinkhole Antipattern:** Ocurre cuando las peticiones atraviesan todas las capas como un "sumidero" sin ejecutar lógica de negocio real (ej. `Controller -> Service -> Repository -> DB` simplemente para retornar un registro). Si más del 20% de las peticiones caen en este flujo, la arquitectura genera un _overhead_ innecesario de memoria y CPU.
2. **Domain Smearing (Dispersión del Dominio):** Al no existir un núcleo de dominio aislado, la lógica de negocio se dispersa entre los controladores, servicios y las propias entidades del ORM.

## 2.2 Práctica: Análisis del Repositorio `attendance-service-layered`

El microservicio `attendance-service-layered` gestiona marcajes de asistencia (`CHECK_IN` / `CHECK_OUT`). El flujo de peticiones es estrictamente sincrónico y descendente: `Controller` $\rightarrow$ `Service` $\rightarrow$ `Repository` $\rightarrow$ `Base de Datos`.

### Acoplamiento entre la Base de Datos y el Dominio

Analicemos la clase `Attendance`. En la arquitectura en capas tradicional, la misma entidad que define el modelo de datos relacional es la que se utiliza para transportar la lógica en la aplicación.

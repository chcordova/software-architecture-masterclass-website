export const codeHexController = `
package com.company.attendance.infrastructure.input.web;

import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/api/v1/attendances")
public class AttendanceController {

    private final RegisterAttendanceUseCase registerAttendanceUseCase;

    public AttendanceController(RegisterAttendanceUseCase registerAttendanceUseCase) {
        this.registerAttendanceUseCase = registerAttendanceUseCase;
    }

    @PostMapping
    public ResponseEntity<AttendanceResponseDto> register(@RequestBody @Valid AttendanceRequestDto dto) {
        Attendance domainModel = dto.toDomain();
        Attendance saved = registerAttendanceUseCase.execute(domainModel);
        return ResponseEntity.created(...).body(AttendanceResponseDto.fromDomain(saved));
    }

}
`;

export const codeHexJpaAdapter = `
package com.company.attendance.infrastructure.output.persistence;

import com.company.attendance.domain.model.Attendance;
import com.company.attendance.domain.ports.out.AttendanceRepositoryPort;
import org.springframework.stereotype.Component;

// DRIVEN ADAPTER: Traduce el Dominio a Infraestructura (Spring/JPA)
@Component
public class AttendanceJpaAdapter implements AttendanceRepositoryPort {

    private final SpringDataAttendanceRepository repository;

    @Override
    public Attendance save(Attendance attendance) {
        AttendanceEntity entity = AttendanceEntity.fromDomain(attendance);
        AttendanceEntity savedEntity = repository.save(entity);
        return savedEntity.toDomain();
    }

}
`;

# Módulo 3: Arquitectura Hexagonal y Diseño Guiado por el Dominio (DDD)

En este módulo exploraremos cómo la **Arquitectura Hexagonal** (_Ports and Adapters_) aísla las reglas de negocio del software frente a marcos de trabajo externos y tecnologías de infraestructura, utilizando el repositorio `attendance-service-hexagonal`.

## 3.1 Teoría: Puertos, Adaptadores y Fidelidad de Datos

Concebida por **Alistair Cockburn**, la **Arquitectura Hexagonal** establece que el núcleo de la aplicación (_Domain Core_) no debe conocer los detalles de cómo se entregan los datos (REST, GraphQL, CLI) ni cómo se persisten (JPA, MongoDB, Archivos).

### Puertos y Adaptadores

- **Puertos (Ports):** Interfaces que definen los contratos de entrada (_Driving Ports_) y salida (_Driven Ports_) del dominio.
- **Adaptadores (Adapters):** Componentes externos que traducen protocolos del mundo exterior hacia o desde los puertos abstractos del dominio.

### La Observación de Eric Evans sobre la Fidelidad de Datos

En la visión inicial de Cockburn, la base de datos era vista como un adaptador intercambiable más. **Eric Evans (creador de DDD)** enriqueció esta postura señalando la **Fidelidad de los Datos** (_Data Fidelity_): en microservicios reales, el modelo de datos relacional y sus transacciones están íntimamente ligados a las reglas del contexto delimitado (_Bounded Context_), por lo que el dominio debe poseer su propio modelo libre de anotaciones de frameworks.

## 3.2 Práctica: Análisis del Repositorio `attendance-service-hexagonal`

El repositorio `attendance-service-hexagonal` desacopla completamente el núcleo de negocio dentro del paquete `domain/`.

### El Costo del Desacoplamiento (Data Mapping)

Lograr esta pureza tiene un costo (_Trade-off_): requerimos mapear objetos constantemente (`DTO` $\leftrightarrow$ `Domain Model` $\leftrightarrow$ `JPA Entity`). Sin embargo, este precio se paga gustosamente para blindar la aplicación frente a cambios tecnológicos futuros.
